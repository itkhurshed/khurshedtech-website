Building a SOC Home Lab on a Budget

By Khurshed Alam · Cybersecurity Engineering Notes

One of the fastest ways to move from "I know security concepts" to "I can actually detect and triage an attack" is building a small Security Operations Center (SOC) lab at home. You don't need enterprise licensing or a rack of servers — a single decent laptop or an old desktop with a few virtual machines is enough to practice real detection engineering end to end.

This is the exact structure I use for my own SOC Home Lab project: a target environment that generates activity, a sensor layer that watches it, and a SIEM that aggregates and alerts on what it sees.

1. Plan the architecture first

Before installing anything, sketch three layers:

  • Targets — one Windows 10/11 VM and one Linux VM, acting as the "endpoints" you're protecting.
  • Sensors — a network intrusion detection engine watching traffic, plus host agents on each target reporting logs.
  • Aggregation & alerting — a central SIEM that ingests everything and lets you search, correlate, and build detection rules.

2. Core tooling (all free/open-source)

  • Wazuh — open-source SIEM and host-based intrusion detection (agents on each endpoint, a central manager and dashboard).
  • Suricata — network intrusion detection engine that inspects traffic against signature rule sets and can feed alerts into Wazuh.
  • VirtualBox or Proxmox — free virtualization to host everything on one machine.
  • Kali Linux — a controlled "attacker" VM used only inside your isolated lab network to generate realistic malicious traffic.
Isolate the lab network. Put every VM on an internal/host-only virtual network with no route to your real home network. You're intentionally generating malicious-looking traffic — it should never reach the internet or your other devices.

3. Build order

  1. Stand up the Wazuh manager and dashboard VM first — this is your "SIEM."
  2. Install Wazuh agents on the Windows and Linux target VMs so host logs (auth events, process creation, file integrity) start flowing in.
  3. Deploy Suricata on a VM positioned to see inter-VM traffic (or on the target hosts themselves) and configure it to forward alerts to Wazuh.
  4. Confirm end-to-end flow: an event on a target should appear as a searchable, alertable entry in the Wazuh dashboard within seconds.

4. Generate real detections, not just green checkmarks

A lab is only useful if you actually break things. From the Kali VM, run a handful of well-known, low-risk simulated attacks against your targets — a port scan, a brute-force login attempt, an EICAR test file — and then go find the alert in Wazuh. Ask yourself the questions a SOC analyst actually asks:

  • What alert fired, and how long after the activity started?
  • What data do I have to confirm this is real and not noise (source IP, process tree, user account)?
  • What would my containment step be, and what log would confirm containment worked?

5. Turn it into a portfolio project

Document each detection you build: the scenario, the rule or query that catches it, and a short write-up of your triage decision. That documentation — not just the running lab — is what turns this into evidence of real analyst skill for interviews and portfolio reviews.
